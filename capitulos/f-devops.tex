\section{Integración con herramientas DevOps}\label{f-0}

Este apartado describe cómo se construye, se prueba y se despliega Economicon de forma automatizada, y qué evidencia deja cada paso. Recorre el flujo de trabajo, la integración continua, los contenedores, el registro y las métricas, el despliegue continuo y la documentación.

\subsection{Flujo de trabajo}\label{f-flujo}

Economicon vincula la ejecución del proyecto mediante un mismo identificador de tarea en Trello, OpenSpec y GitHub. Trello conserva alcance, responsables y estado; OpenSpec define requisitos y escenarios de aceptación en el propio repositorio; GitHub conserva código, documentación, decisiones técnicas y revisiones. Las ramas de tarea proponen cambios a la rama de desarrollo (develop), mientras que la rama principal (main) representa la línea estable. El proceso separa liderazgo, trabajo en pareja (pairing), revisión y validación: una asignación de rol o una comprobación automática no demuestra por sí sola participación ni aceptación humana. \cite{gobierno,adr-registro}

\subsection{Integración continua}\label{f-ci}

La integración continua (CI) se ejecuta en GitHub Actions ante un envío de rama (push), una solicitud de cambios (pull request) a develop o main, por activación manual y como flujo reutilizable por el despliegue continuo (CD). En Ubuntu, el flujo prepara Node.js 22 y Python 3.12. Comprueba trazabilidad, higiene del repositorio y OpenSpec; ejecuta las suites de pruebas de backend, processor y API de costes; y verifica el análisis de estilo, las pruebas, la construcción y los tipos del frontend. En Python, compileall comprueba sintaxis y compilación a bytecode, sin sustituir un análisis de estilo. Las dependencias del workspace se instalan con las versiones exactas fijadas en el fichero de bloqueo. \cite{integracion}

La evidencia de la integración continua recoge una ejecución de pull request del 05/10/2026 con siete jobs correctos y otra de push con los seis técnicos correctos y la política de PR omitida, como corresponde a ese evento. Esos resultados pertenecen a aquella entrega. La CI comprueba estáticamente la topología Docker y prueba las herramientas de diagnóstico; no construye ni arranca el stack completo. Las pruebas que requieren servicios reales y se omiten en una ejecución no acreditan esa integración. Por ello, los ensayos con contenedores se documentan separadamente. \cite{integracion}

\subsection{Contenedores y entorno local}\label{f-docker}

Cuatro Dockerfiles empaquetan frontend, backend, processor y API de costes. Docker Compose conecta las aplicaciones con sus bases de datos, RabbitMQ, Prometheus y Grafana. Las aplicaciones cuentan con comprobaciones de salud (healthchecks), usuario sin privilegios (no root) y controles de ejecución definidos en Compose; sus imágenes base están fijadas por huella (digest). Este endurecimiento no se extiende de forma idéntica a todos los servicios auxiliares. local:doctor comprueba la preparación del entorno y local:smoke, una prueba de humo, recorre salud, autenticación demo, ingesta y procesamiento. Un primer ensayo documenta la construcción y la prueba de humo en DockerServer; un segundo acredita arranque, prueba de humo, un control negativo con el processor detenido y persistencia tras reiniciar en Docker Desktop. Son entornos de ensayo, con datos de prueba y proveedores simulados, no una certificación de producción. \cite{docker}

\subsection{Registro y métricas}\label{f-observabilidad}

El registro de backend y processor emite eventos JSON a la salida estándar con fecha, servicio, nivel y contexto. Cada petición recibe un identificador (request\_id). En POST /jobs/ingest, el backend lo transmite en el mensaje de RabbitMQ; el worker conserva el identificador válido o genera otro si falta o es inválido. Así puede seguirse el recorrido de una ingesta asíncrona y sus errores. Los eventos HTTP registran método, plantilla de ruta, estado y duración, y se redactan campos sensibles. Las pruebas y su evidencia verifican esa correlación, incluidos reintentos; no acreditan trazas distribuidas completas ni cobertura de todos los procesos batch. \cite{convenciones}

Prometheus consulta los endpoints /metrics de backend y processor cada 15 segundos. Los contadores e histogramas alimentan un panel provisionado en Grafana con la latencia p95 (el tiempo que no supera el 95\,\% de las peticiones), los errores 5xx (fallos del servidor), las ingestas, las consultas y las alertas. La regla detecta un incremento superior a dos marcas de fallo persistidas en una ventana móvil de cinco minutos y exige que la condición se mantenga dos minutos: cuenta también reintentos, no trabajos únicos. La evidencia de alertas registra la transición hasta el estado de disparo (Firing); una prueba posterior usó un exportador de métricas sintético. Esta instrumentación permite diagnóstico técnico, pero no constituye un objetivo de nivel de servicio (SLO) demostrado ni una evaluación de calidad de las respuestas. No se acredita un receptor externo de alertas. \cite{monitorizacion}

\subsection{Despliegue continuo}\label{f-cd}

El despliegue continuo privado se integró en develop el 11/10/2026 mediante una pull request. GitHub Actions reutiliza la CI para declarar elegible una versión concreta del código (SHA); un agente pull en DockerServer descarga esa revisión, prepara una release aislada, comprueba disponibilidad y ejecuta cinco verificaciones funcionales antes de promoverla. El diseño incluye bloqueo de concurrencia, puertos accesibles solo desde la propia máquina (loopback), secretos locales y recuperación. El entorno es de desarrollo y validación, con datos desechables y proveedores simulados. El rollback reactiva la release anterior con sus propios volúmenes; no revierte migraciones ni recupera los datos de la release retirada. \cite{despliegue}

La primera promoción automática integrada quedó acreditada el 11/10: la evidencia de cierre registra el mismo enlace a la versión activa (current) y el mismo identificador de ejecución (run\_id), cinco pruebas de humo de cinco y nueve contenedores en marcha con once puertos publicados solo en loopback. Una lectura posterior del estado y del registro del sistema confirma una segunda promoción, cuya release anterior es la primera. El ensayo local anterior, sin identificador de ejecución (run\_id=null), se conserva como evidencia histórica distinta. Las cinco comprobaciones recorren salud, login, ingesta simulada, facturación y job RabbitMQ. \pendiente{} recuperación tras reiniciar el host y validación integral de producción. La promoción simulada no demuestra calidad de respuestas ni inferencias reales. \cite{despliegue}

\subsection{Documentación}\label{f-documentacion}

La documentación mantiene el vínculo entre cada decisión, su implementación y sus límites: README y manuales para ejecutar, decisiones de arquitectura (ADR) para justificar alternativas y los ficheros de evidencia para reproducir verificaciones. El registro de decisiones reúne ese vínculo sin convertir automáticamente propuestas en decisiones ratificadas; las decisiones sobre métricas y despliegue continuo conservan el estado «propuesta» en las fuentes consultadas. \cite{gobierno,adr-registro,monitorizacion,despliegue}
