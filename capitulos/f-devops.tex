\section{Integración con herramientas DevOps}\label{f-0}

Economicon vincula la ejecución del proyecto mediante un mismo identificador JUP en Trello, OpenSpec y GitHub. Trello conserva alcance, responsables y estado; OpenSpec define requisitos y escenarios de aceptación; GitHub conserva código, documentación, decisiones técnicas y revisiones. Las ramas de tarea proponen cambios a develop, mientras main representa la línea estable. El proceso separa liderazgo, pairing, revisión y validación: una asignación de rol o un check automático no demuestra por sí solo participación ni aceptación humana. \cite{contributing,adr-indice}

La integración continua se ejecuta en GitHub Actions ante un push de rama, una pull request a develop o main, por activación manual y como workflow reutilizable por CD. En Ubuntu, el workflow prepara Node.js 22 y Python 3.12. Comprueba trazabilidad, higiene del repositorio y OpenSpec; ejecuta las suites de backend, processor y API de costes; y verifica lint, pruebas, build y tipos del frontend. En Python, compileall comprueba sintaxis y compilación a bytecode, sin sustituir un análisis de estilo. Las dependencias del workspace se instalan con el lockfile congelado. \cite{ci-workflow,jup051}

La evidencia de JUP-051 recoge una ejecución de pull request del 05/10/2026 con siete jobs correctos y otra de push con los seis técnicos correctos y la política de PR omitida, como corresponde a ese evento. Esos resultados pertenecen a aquella entrega. La CI comprueba estáticamente la topología Docker y prueba las herramientas de diagnóstico; no construye ni arranca el stack completo. Las pruebas que requieren servicios reales y se omiten en una ejecución no acreditan esa integración. Por ello, los ensayos con contenedores se documentan separadamente. \cite{ci-workflow,jup051}

Cuatro Dockerfiles empaquetan frontend, backend, processor y API de costes. Docker Compose conecta las aplicaciones con sus bases de datos, RabbitMQ, Prometheus y Grafana. Las aplicaciones cuentan con healthchecks, usuario no root y controles de ejecución definidos en Compose; sus imágenes base están fijadas por digest. Este endurecimiento no se extiende de forma idéntica a todos los servicios auxiliares. local:doctor comprueba la preparación del entorno y local:smoke recorre salud, autenticación demo, ingesta y procesamiento. JUP-049 documenta construcción y smoke en DockerServer; JUP-050 acredita arranque, smoke, un control negativo con el processor detenido y persistencia tras reiniciar en Docker Desktop. Son entornos de ensayo, con datos de prueba y proveedores mock, no una certificación de producción. \cite{docker-compose,jup049,jup050}

El logging de backend y processor emite eventos JSON a la salida estándar con fecha, servicio, nivel y contexto. Cada petición recibe un request\_id. En POST /jobs/ingest, el backend lo transmite en el mensaje de RabbitMQ; el worker conserva el identificador válido o genera otro si falta o es inválido. Así puede seguirse el recorrido de una ingesta asíncrona y sus errores. Los eventos HTTP registran método, plantilla de ruta, estado y duración, y se redactan campos sensibles. Las pruebas y la evidencia de JUP-044 verifican esa correlación, incluidos reintentos; no acreditan trazas distribuidas completas ni cobertura de todos los procesos batch. \cite{convenciones-python,jup044-revision}

Prometheus consulta los endpoints /metrics de backend y processor cada 15 segundos. Los contadores e histogramas alimentan un dashboard provisionado en Grafana con latencia p95, errores 5xx, ingestas, consultas y alertas. La regla detecta un incremento superior a dos marcas de fallo persistidas en una ventana móvil de cinco minutos y exige que la condición se mantenga dos minutos: cuenta también reintentos, no trabajos únicos. JUP-045 registra la transición de alerta hasta Firing; una prueba posterior usó un exporter sintético. Esta instrumentación permite diagnóstico técnico, pero no constituye un SLO demostrado ni una evaluación de calidad de las respuestas. No se acredita un receptor externo de alertas. \cite{prometheus-config,jup045}

El despliegue continuo privado de JUP-052 se integró en develop el 11/10/2026 mediante la PR \#73. GitHub Actions reutiliza la CI para declarar elegible un SHA; un agente pull en DockerServer descarga esa revisión, prepara una release aislada, comprueba disponibilidad y ejecuta cinco verificaciones funcionales antes de promoverla. El diseño incluye bloqueo de concurrencia, puertos loopback, secretos locales y recuperación. El entorno es de desarrollo y validación, con datos desechables y proveedores mock. El rollback reactiva la release anterior con sus propios volúmenes; no revierte migraciones ni recupera los datos de la release retirada. \cite{guia-cd,pr73}

La primera promoción automática integrada quedó acreditada el 11/10: la evidencia de cierre registra el mismo current y run\_id, smoke 5/5 y nueve contenedores en marcha con once puertos publicados sólo en loopback. Una lectura posterior de estado y journal confirma una segunda promoción, cuya release anterior es la primera. Esto supera el pendiente del borrador del 10/10; el ensayo local anterior con run\_id=null se conserva como evidencia histórica distinta. Las cinco comprobaciones recorren salud, login, ingesta simulada, facturación y job RabbitMQ. \pendiente{} recuperación tras reiniciar el host y validación integral de producción. La promoción mock no demuestra calidad de respuestas ni inferencias reales. \cite{guia-cd,pr73,run-cd}

La documentación mantiene el vínculo entre cada decisión, su implementación y sus límites: README y manuales para ejecutar, ADR para justificar alternativas y docs/evidence/ para reproducir verificaciones. JUP-061 reúne ese registro sin convertir automáticamente propuestas en decisiones ratificadas; ADR-0005 de métricas y ADR-0018 de CD conservan el estado Proposed en las fuentes consultadas. \cite{contributing,adr-indice,prometheus-config,jup045,guia-cd,pr73}
