\section{Arquitectura técnica de la solución}\label{d-0}

La arquitectura separa la interfaz, las reglas de negocio y el procesamiento de documentos para poder evolucionarlos y operarlos de forma independiente. La versión implementada tiene un entorno local reproducible y adaptadores opcionales para AWS. Distinguir qué está integrado, qué se activa por configuración y qué se ha ensayado evita confundir una capacidad del código con un despliegue aceptado. \subsection{Datos, documentos y conversación}\label{d-1}

La API concentra autenticación, autorización y consultas; el processor ejecuta trabajos largos sin mantener abierta la petición de subida. CockroachDB guarda el estado operativo y PostgreSQL con pgvector los textos y vectores. MinIO almacena los originales mientras son necesarios. Esta separación explicita responsabilidades, pero no demuestra una ventaja de rendimiento ni crea una transacción distribuida entre base de datos y cola. La confirmación de publicación en RabbitMQ no equivale a procesamiento exactamente una vez. \cite{arquitectura-final}

La ingesta acepta texto o un archivo original. Para un archivo, el navegador obtiene una URL firmada de vida corta, lo sube a MinIO y solicita su confirmación. El backend verifica tamaño, contenido y formato antes de publicar el trabajo. El processor descarga el original confirmado, extrae texto en un entorno aislado, fragmenta, genera embeddings y persiste los resultados. Tras el éxito durable retira el original; la caducidad del área de subida limpia los archivos abandonados. Por tanto, la referencia al artefacto participa en un recorrido de descarga y extracción, no es sólo un metadato. \cite{arquitectura-final}

Hay dos recorridos de consulta. El determinista resuelve peticiones explícitas de gasto, presupuestos, propiedad y anomalías con reglas del servidor y recuperación documental. El generativo se habilita expresamente en backend y processor: la API comprueba cliente y propietario, registra la operación y llama al processor por una red privada. La petición lleva una firma HMAC, un código que verifica integridad y autenticidad mediante una clave compartida, y una protección contra reutilización. El servidor recupera contexto una vez por intento antes del borrador; el modelo redacta y el navegador recibe texto, estado y fuentes en flujo. Se conservan historial y operaciones para consultar, detener o reanudar. El modelo no ejecuta SQL ni elige herramientas FinOps. \cite{arquitectura-final}

Los costes proceden de una API Azure simulada y de muestras públicas o sintéticas. Su ingesta es independiente de la documental. Las consultas agregan registros completados por intervalo y moneda; los presupuestos evalúan gasto observado y las anomalías usan reglas. No generan previsiones ni acreditan ahorro real. La recuperación híbrida está implementada, pero apagada por defecto y requiere preparar el índice. Los límites de calidad del chat se detallan en el apartado~\ref{h-0}. \cite{arquitectura-final}

\subsection{Seguridad, operación y entrega}\label{d-2}

La autorización combina el token de acceso firmado, la membresía y el cliente seleccionado: enviar su identificador no concede acceso. Las conversaciones se restringen al propietario y los documentos al cliente autorizado. El processor vuelve a comprobar propietario y reserva de gasto antes de generar; su API de chat no publica un puerto al exterior. Las credenciales se suministran mediante configuración protegida. Estos controles no certifican por sí solos revocación completa, autenticación multifactor ni endurecimiento productivo. \cite{arquitectura-final}

Compose reproduce dependencias y datos simulados. Sus publicaciones de puertos, el modo local de CockroachDB y la previsualización del frontend requieren controles adicionales para exposición pública. Los logs estructurados e identificadores de petición permiten correlacionar eventos; Prometheus recoge métricas y Grafana las presenta, sin equivaler a trazabilidad distribuida completa ni a un receptor externo de alertas. La integración y el despliegue continuos se describen en el apartado~\ref{f-0}; los ensayos observados, en el apartado~\ref{h-0}. \cite{arquitectura-final,ci-final}

\subsection{Alternativa AWS y estado de implementación}\label{d-3}

La figura~\ref{fig-d1} muestra la distribución de referencia en AWS: frontend en S3 privado y CloudFront; backend y processor en ECS Fargate; acceso a la API mediante un balanceador interno; RabbitMQ gestionado y PostgreSQL para datos operativos y vectores. Cognito aporta identidad y Bedrock la ruta nativa de modelos. El esquema es una referencia de despliegue, no evidencia de servicios operativos en la nube. \cite{arquitectura-final,aws-ensayo}

\figura{arquitectura-aws-referencia}{Distribución de referencia en AWS; no representa un despliegue de la aplicación verificado. \cite{arquitectura-aws}\label{fig-d1}}

Los adaptadores de PostgreSQL operativo, Cognito y Bedrock ya están implementados y tienen comprobaciones locales o sin conexión. También existe el código de dos pipelines manuales de creación y retirada de un ciclo desechable, con CodePipeline, CodeBuild y CDK/CloudFormation. Terraform se conserva como alternativa de aprovisionamiento; no implementa esos pipelines. Estas capacidades están desactivadas por defecto y la evidencia citada no acredita una aplicación desplegada en AWS, un inicio de sesión real contra Cognito ni invocaciones a Bedrock. La preparación de infraestructura y la aceptación del ensayo son estados distintos. \cite{arquitectura-final,aws-ensayo,terraform-validacion}
